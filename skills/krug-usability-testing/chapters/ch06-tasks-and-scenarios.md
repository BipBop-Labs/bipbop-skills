# Chapter 6: Find some things for them to do

## Core Idea
Choose the **tasks** that matter most this month, then write them up as **scenarios**: short scripts that give context without giving clues. Pilot them, then print them.

## Frameworks Introduced
- **Two steps**: (1) choose **tasks**, the things you want them to try; (2) expand them into **scenarios**, which add the context they need.
- **Step 1, the task list**: write down 5–10 of the most important things people need to do with your product. Teams almost always agree on this list. The trick is to make it reflect **users' actual goals, not your idea of what they want to do.**
- **Step 2, pick this round's tasks** using three filters:
  1. **Critical tasks**: things people *must* be able to do or the product fails (find a book, pay for it).
  2. **"What's keeping you awake at night?"**: things you suspect confuse people.
  3. **Other research signals**: what customer support hears repeatedly, and red flags in analytics.
- **Time budget**: in a 50-minute session you get about **35 minutes of task time**. That could be one long task or up to ten short ones. **Always have extra tasks** for fast participants. A good filler is doing a task on a competitor's site.
- **Scenario anatomy**: like an improv card, it gives character, motivation, what to do, and a few details. "You are…", "You need to…", plus information they need but wouldn't have, such as test-account credentials. **Trim any detail that doesn't contribute.**
- **The one hard rule: don't give clues.** Write it clear and unambiguous **without using uncommon or unique words that appear on the screen**. Otherwise the task becomes a word-finding game.
  - Bad: "Customize your LAUNCHcast station."
  - Better: "Choose the kind of music you want to listen to."
- **Two optional restrictions ("Don't fence me in")**:
  - **Don't use search**, unless you're testing search. Otherwise you're only testing search results. State it up front and remind them if they forget.
  - **Stay on this site**: don't say it up front. Mention it only when they stray: "For the purposes of this test, I'd like you to stay on this site for now."
- **Pilot test**: about 15 minutes, a day or two before, with almost anyone (friends and family are ideal). Read each scenario and have them *start* each task. Ambiguities show up immediately.
- **Print twice**:
  - **For participants**: one scenario per sheet in large type (print two per page and cut). **Don't number them**, so you can reorder or skip.
  - **For you and observers**: all scenarios on one page.

## Key Concepts
- **Task**: a goal ("buy the book").
- **Scenario**: the task wrapped in context and needed data, phrased without the UI's vocabulary.
- **Filler task**: a spare task for fast participants.
- **Pilot test**: a dry run of the scenarios only, not the whole session.

## Mental Models
- **Test goals, not features.** A task names what the user wants to accomplish, never the control that accomplishes it.
- **If the scenario contains the link text, the result tells you nothing.**

## Anti-patterns
- Tasks that mirror your feature list instead of user goals.
- Scenario wording lifted from labels on screen.
- Over-detailed backstory that participants must remember.
- Numbered task sheets, which lock the order.
- Too few tasks, leaving a participant idle with time on the clock.
- Skipping the pilot, then losing session time to a confusing scenario.

## Worked Example: from task list to scenario
Krug's own list for his site: get info about workshops; sign up for a workshop; read a sample chapter; buy the book; find out about consulting.
Turning "sign up for a workshop" into a scenario *(illustrative)*:
> You manage a small web team and want to learn how to run usability tests yourselves. You'd like to attend a one-day training in person sometime in the next few months. See whether there's one you could go to, and if there is, get yourself a place in it. Use the test account details below if asked.
The scenario gives a motivation (a team lead wanting to learn), a constraint (in person, soon), and a goal (get a place). It avoids the site's own words: no "Register", "Workshops", or "Events" if those are the link labels.

## Key Takeaways
1. Start from 5–10 key user goals, then pick this round's by criticality, worry, and support or analytics signals.
2. Plan about 35 minutes of tasks per 50-minute session, plus fillers.
3. Scenarios add context and required data, and nothing else.
4. Never use the interface's own words in a scenario.
5. Ban search unless you're testing it. Handle straying off-site only when it happens.
6. Pilot the scenarios, then print them unnumbered, one per sheet.
